**Required changes**
1. **A run that stays queued never stops the pipeline** (`.claude/skills/pipeline/SKILL.md`, "CI
   wait", step 3). D-075, the task's Do item and step 4 itself make "a run still queued" a Stop for
   the owner. But `gh run watch` returns only when the run completes (its help: "Watch a run until
   it completes"), and step 3 says that when the call reaches its time limit "with the run still
   going, call it again". So a run that stays queued, as in a GitHub Actions outage, is watched
   again and again, with no end and no notification, and step 4's "or a run still `queued` then"
   is never reached. Change step 3 so that, when a `gh run watch` call reaches its time limit, the
   pipeline reads the run's status (`gh run view <databaseId> --json status --jq .status`):
   `completed` → step 4; `in_progress` → call `gh run watch` again; `queued` or any other status →
   **Stop** (a run still queued 10 minutes after the push). Nothing else changes: `builder.md`,
   `workflow.md` and D-075 already list the case. It is a text change in the skill, so no test can
   fail without it: put the new step 3 in the fix-round row; the delta review reads it.

**Suggestions** (not blocking; each is also a line on the board's Discovered list)
1. **Step 4's two rules overlap on an empty list.** "every name in `failed` starts with `pnpm `" is
   also true when `failed` is empty, which the next bullet makes a Stop. Write "`failed` is not
   empty, and every name in it starts with `pnpm `".
2. **Step 2 can take a broken `gh` for "no run", and can find two runs.** The loop sends `gh`'s
   errors to `/dev/null`: when `gh` is not found in that shell, or its login has expired, the loop
   waits its full 10 minutes and the Stop names the wrong cause. And a pull request that is closed
   and reopened has two runs for one commit and branch; the step does not say which counts. Let
   the loop's errors through (or run `gh auth status` in the same shell first), and take the newest
   run, the first one `gh run list` prints.
3. **A merge conflict looks like "no run".** GitHub starts no `pull_request` run while the pull
   request has a merge conflict with `main` (GitHub's documentation of the `pull_request` event).
   Every role edits the board's "Last updated" line, so a planning branch merged while a task is
   open makes such a conflict likely, and the pipeline then stops with "no run 10 minutes after the
   push". Name a merge conflict as the first thing to check in that Stop (skill step 2,
   `workflow.md`'s Stop list).
4. **`pnpm check` is no longer all that CI checks.** `CLAUDE.md`'s Commands table still calls it
   "Everything a task must pass", and `builder.md`'s "When done" runs only that. CI also fails on
   `pnpm build`, the Auckland steps and `pnpm audit --prod`, so such a failure shows up only in CI
   and costs one of the two fix rounds. Point that row to "CI", or have builders also run
   `pnpm build` before they push (an owner or architect choice).
5. **README's prerequisites** say agents use `gh` "to open pull requests"; the pipeline now also
   needs it logged in to wait for CI (its preconditions run `gh auth status`).
