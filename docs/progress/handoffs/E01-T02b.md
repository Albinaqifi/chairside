- libphonenumber-js 1.13.13: `validatePhoneNumberLength(text, country)` names an impossible input
  (`TOO_SHORT`, `TOO_LONG`, `INVALID_LENGTH`, `NOT_A_NUMBER`, `INVALID_COUNTRY`; only `undefined`
  is possible) and agreed with `isPossiblePhoneNumber` on 300,000 inputs. Store
  `parsePhoneNumberFromString(text, { defaultCountry, extract: false }).number`: the default parse
  picks a number out of other text (`Phone: 070 001 234`). Trim first (a space before `+` is
  `NOT_A_NUMBER`); `isSupportedCountry` first, as `phoneAsWritten` does. With `MK`: `070 001 234`,
  `+389 70 001 234`, `00389 70 001 234` and `+389 (0)70 001 234` give `+38970001234`; `070 001 23`
  gives `+38907000123` (national number `07000123`), possible, not valid; `070 001 234 ext 5` gives
  `+38970001234` with `ext` `5`; `+389 99 123 456` is possible, not valid; `+39 06 1234 5678` is
  valid, its national number `0612345678` (as are numbers of the Vatican, San Marino, Côte d'Ivoire,
  Benin and Congo). The trunk prefix has no typed accessor (`NumberingPlan` in `types.d.ts`): hence
  the task's rule, `0` and not valid. `+49 30 1234567890123` passes the length check (as do long
  numbers of JP, ID and KR) and gives 17 digits, which `phone_e164`'s check (`^\+[1-9][0-9]{1,14}$`)
  refuses: an insert would answer `internal`, hence the task's 15-digit refusal. A number copied
  from WhatsApp, Teams or Outlook comes wrapped in direction marks (U+202A … U+202C, U+200E): the
  strict read calls it `NOT_A_NUMBER`, and `trim()` keeps them, hence their removal. Non-throwing
  calls only (`parsePhoneNumberWithError` throws). `00` works because it is MK's own international
  prefix: test in MK, write no rewrite.
- Zod 4.6.5 with `parseInput`: `z.string()` takes `''`, so a required field is `.trim().min(1)`; a
