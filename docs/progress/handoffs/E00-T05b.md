**For the builder: what is already there** (checked on `main` at `a607fff`; probes thrown away)
- `createStaffUser()` (`src/modules/auth/users.ts`) makes a person through the library's internal
  adapter: `createUser` (email trimmed and lower-cased, `emailVerified: true`), then `linkAccount`
  with the hashed password (`providerId: 'credential'`). The seed calls it with a password and a fixed
  id; that path stays as it is.
- better-auth 1.7.7 (installed; `package.json` says `^1.7.7`). Its `/reset-password`
  (`dist/api/routes/password.mjs`) takes `newPassword` and `token`, checks the length,
  `consumeVerificationValue('reset-password:' + token)` (deletes the row under a lock; null when
  missing or expired), makes the credential account when the person has none, else updates it, then
  ends the person's sessions (`revokeSessionsOnPasswordReset: true` is set). Missing, wrong, used and
  expired all answer `INVALID_TOKEN`. `/request-password-reset` stays off (no `sendResetPassword`).
- The internal adapter has `findUserByEmail`, `findCredentialAccount` and
  `createVerificationValue({ identifier, value, expiresAt })`; the last stores the identifier as
  `verification.storeIdentifier` says: `'plain'` by default, `'hashed'` = SHA-256, base64url
  (`dist/db/verification-token-storage.mjs`; typed in `@better-auth/core`'s `init-options.d.mts`). No
  verification rows are made today, so `'hashed'` for all is safe. The library's own tokens are 24
  characters (about 143 bits); Node's `crypto` gives the same.
- Grants today (`0000_init.sql`, `0001_auth.sql`): `clinics` SELECT, UPDATE; `memberships` SELECT
  (its comment foresees the operator script's own grant); `audit_log` SELECT, INSERT; `users` and
  `accounts` SELECT, INSERT, UPDATE (no DELETE: the app never deletes a person); `verifications` all
  four. `clinics`'s policy compares `id` with `current_clinic_id()`: inside `withTenant(newId)` an
  insert of that very id passes, any other fails.
- `audit.record(tx, entry)` takes its clinic from `current_clinic_id()`, so it needs the new clinic's
  `withTenant`; actor `system` has `actorId: null`; metadata with a personal field name throws.
- Lint allows `withTenant` in `src/db/`, where the script lives and may import `@/modules/*`, as the
  seed does. `withTenant` checks that the id is a UUID, not that the clinic exists.
- The guard: `connectionTarget()` and `checkLocalTargets()` in `src/db/reset.ts` (this machine is
  `localhost`, `127.0.0.1`, `::1`, as pg reads the URL, its query parameters included). The seed's
  guard also refuses `NODE_ENV=production`: this script must not, as it will run in production.
- `clinicsForUser(userId)` (auth module): a person's active memberships in every clinic, through
  `clinics_for_user()`; empty for a person a broken run left behind.
- The login page (`src/app/(auth)/login/`): `page.tsx` is public on purpose and says so;
  `login-form.tsx` posts to `/login`, its button disabled until the script runs, a `<noscript>`
  line; `authClient` is `src/app/_lib/auth-client.ts`. The `(auth)` layout checks nothing; the proxy
  skips every path that starts with `login`.
- `isSupportedCountry` (libphonenumber-js 1.13.13, D-097): `UK` is not supported, `GB` is.
  `Intl.DateTimeFormat` with an unknown `timeZone` throws a RangeError.
- `pnpm db:generate --custom --name <what>` gives an empty migration for SQL only (drizzle-kit
  0.31's `--custom`), with its `meta/` entry: 0004 changes no `schema.ts`.
- Traps. (1) The person is made on the library's own connection, outside `withTenant`, so the two
  share no transaction, and the app role cannot delete a person: hence "taken up by the next run",
  not undone. One order leaves nothing in the way: person, token, the clinic's transaction, print; a
  broken transaction leaves an unprinted token nobody has, which expires. (2) A run for a person
  who already has a clinic makes no token: two live tokens would let the older one reset a password
  already chosen. (3) The link's maker takes `now` (module rule 4), so a test makes an expired token
  with a `now` four days back. (4) An end-to-end run signs in at most seven times (D-100): the
  page's check sets a password and stops; the integration test proves the sign-in. (5) The page's
  title goes through `generateMetadata`, as the login page's does.
- Not to change: the seed's use of `createStaffUser()`, `withTenant`, the proxy, the login form.
