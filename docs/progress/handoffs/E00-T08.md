**For the builder: what is already there** (checked in the code on `main` at `0c15bbb`)
- The wrappers `staffAction`, `staffRead` and `userAction` are exported from
  `src/app/_lib/actions.ts`. That file is not a `'use server'` file (it only mentions the words in
  a comment) and must not be reported. `staffRead(…)` returns the action with `forPage` attached
  (`Object.assign`), so `staffRead(…).forPage` is a member expression on the call.
- The only `'use server'` file is `src/app/(auth)/choose-clinic/actions.ts`, with
  `export const chooseClinic = userAction(…)`. The only route handler is
  `src/app/api/auth/[...all]/route.ts`.
- Database imports today: `@/db/client` in `src/db/` and in `src/modules/auth/` (`better-auth.ts`,
  `memberships.ts`). Outside `src/db/`, `withTenant` is value-imported only in
  `src/app/_lib/actions.ts`. `src/modules/audit/record.ts` and `src/modules/auth/memberships.ts`
  import `TenantTransaction` as a type.
- `eslint.config.mjs` already sets `no-restricted-imports` for `src/modules/**` (no Next.js or
  React). In a flat config, a later block that sets the same rule for the same files replaces its
  options instead of adding to them. A database-import restriction written as a second
  `no-restricted-imports` must keep the framework patterns for modules, or the framework cases in
  `architecture.test.ts` fail.
- typescript-eslint 8.71.0 comes with `eslint-config-next`; its plugin has
  `no-floating-promises`, `no-misused-promises` and `only-throw-error`. No new dependency (D-071).
  These rules need type information (`parserOptions.projectService` or `project`).
- **The snippet linter and type information.** `architecture.test.ts` lints snippets through
  `eslint-rules/lint-snippets.mjs` (`ESLint.lintText`) at paths that do not exist on disk, such as
  `src/modules/scheduling/slots.ts`. A scratch probe on `0c15bbb` (not committed): with
  `projectService: true`, such a snippet gets only a parsing error ("… was not found by the
  project service") and no rule runs, so every existing case would fail. With
  `projectService: { allowDefaultProject: [<the snippets' folders>] }`, both promise rules and
  `only-throw-error` reported as expected. How to solve it is your choice (`allowDefaultProject`,
  options only the snippet runner passes, or temporary files); every existing case keeps passing
  unchanged (rule 8).
- `only-throw-error` with its defaults: `throw withoutQueryValues(error)` (it returns `unknown`)
  and a rethrown caught error pass; `throw refuse(…)` is reported (a `Refusal` is not an Error).
  Today every other `throw` in `src/` throws a new instance of an Error class (`TypeError`,
  `HandlerRefused`, the auth library's `APIError`…), so no existing finding is expected from it.
- Login rows: `clinicsForUser(userId)` (`src/modules/auth/memberships.ts`) already lists a
  person's active memberships across clinics. `audit.record(tx, entry)` (`@/modules/audit`) takes
  `at`, `actorType: 'user'`, `actorId`, `action: 'user.logged_in'`, `entityType`, `entityId`, and
  refuses ids that are not UUIDs (user ids are UUID v7, from `newId()`). The auth library is set up
  in `src/modules/auth/better-auth.ts` (`createAuth()`); there are no `databaseHooks` yet.
  `audit` does not import `auth`, so the hook can import `@/modules/audit` without a cycle.
- The proxy (`src/proxy.ts`) redirects every request without a valid session to `/login`, server
  actions included. Its tests are in `tests/integration/auth-proxy.test.ts`; the grant-taking
  helper for the failed login row is `withoutGrant` in `tests/integration/fixtures.ts`.
