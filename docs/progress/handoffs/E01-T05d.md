**What was settled** (the architect's, inside the task's words; no decision entry: nothing here makes
a document untrue or adds a dependency)
- **The same booking sent twice books one patient once.** `already_booked` (E01-T05b) matches the
  patient's id; a second send of a new patient (a second tab, an answer lost, "Book anyway" sent
  again) would make a new id, so the first patient's visit would read as another patient's: an
  overlap without "anyway", a second patient and a second visit with it, two reminders to one phone
  (`message`; `test-strategy.md`, Duplicates). The drawer makes the new patient's id once per opening
  and sends it; `patients.create` takes it and writes nothing when that id exists; the handler then
  books that patient as a picked one, and the booking is `already_booked`.
- **"Add “…” as new patient"** is the suggestion list's last option from the third character (the
  demo's `nq.length > 2`), with or without suggestions; the arrow keys reach it and Enter takes it.
- **What was typed fills the fields:** the last word the last name, the rest the first name; a text
  that reads as a phone goes to the phone field (the search takes a phone too, E01-T02a).
- **The second permission:** the action keeps `calendar.manage`; before it writes a patient the
  handler asks `can(…, 'patients.manage')`, so narrowing who adds patients later cannot be passed by
  booking. Every role has both today (`src/modules/auth/permissions.ts`), so no test reaches the
  refusal: a review check.
- The language is the new-patient page's start (the message file's first, `en`); the date of birth,
  guardian and notes stay on the profile (E01-T03).
