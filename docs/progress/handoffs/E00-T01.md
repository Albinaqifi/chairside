**Findings** (what I did, what happened, what should happen)

Must fix in this task (failing tests added):

1. **The logger writes the values of a failed database query. (High)** I made a real query fail
   inside `withTenant`: an update whose `name` value was a synthetic marker and whose currency
   broke the check constraint. I logged the error as `logger.error({ err })`, `logger.error(err)`
   and `logger.error({ error })`. Drizzle wraps the Postgres error in `DrizzleQueryError`: its
   `message` and `stack` end with `params: <the values>`, and its `params` field holds them. The
   logger keeps all three, so the marker was in `err.message`, `err.stack` and `err.params[0]`,
   and with `logger.error(err)` also in `msg` (pino copies the error message there). The
   Postgres `detail` was dropped correctly. **Should:** no value a query was sent ever reaches a
   log line; the SQL text with `$1` placeholders and the error code may stay. Otherwise every
   failed patient insert puts names and phone numbers into the logs, and the E00-T03 wrapper will
   log caught errors. Test: `tests/integration/log-redaction.test.ts`.
2. **A `withTenant` call inside another `withTenant` call can wait forever. (High, reliability)**
   (a) The outer call updates a clinic row, then a nested call updates the same row. The nested
   transaction waits for the outer one's lock while the outer one waits for the nested call.
   PostgreSQL cannot see this as a deadlock (two connections) and nothing times out. (b) With as
   many outer calls at once as the pool has connections (10), each making one nested call, every
   nested call waits for a connection forever, with no row conflict at all. Both hang with no
   error and no log line. **Should:** never wait forever. Any of these passes the tests: refuse a
   nested call with a clear error, run it inside the outer transaction, or fail with a timeout
   within 10 s (pool `connectionTimeoutMillis`, `lock_timeout`). This is a choice about
   `withTenant`'s contract: the builder proposes, the owner decides. It matters now because module
   functions calling each other (E00-T03 onward) will nest calls naturally, and (b) shows only
   under load. Test: `tests/integration/tenant-nesting.test.ts`.
3. **`fakeClock` accepts days that do not exist. (Low)** `fakeClock('2026-02-30T09:00:00Z')`
   gives 2 March; `2026-02-29` (not a leap year) gives 1 March; `set()` does the same. **Should:**
   throw `RangeError`, like other invalid input. The recall and timing tests the test strategy
   lists (29 February, month ends) would otherwise run on a date they did not ask for. Test: the
   new case in `src/lib/clock.test.ts`.

pool plus lock timeouts; stripping `params`; a day-of-month check. All tests, the builder's

5. **The app role can create temporary tables, and one can stand in for a real table for the next
   clinic. (Medium)** Inside `withTenant(A)`: `create temp table audit_log as select * from
   public.audit_log`. The next `withTenant(B)` on the same pooled connection read `audit_log` and
   got clinic A's rows. Cause: PUBLIC has the TEMPORARY privilege on a new database; temp tables
   outlive the transaction and are found first. No normal code does this, but it is a cross-clinic
   read through `withTenant` that R-31's review rule (look for `app.clinic_id`, `set_config`)
   would not catch. Suggest: `REVOKE TEMPORARY ON DATABASE … FROM PUBLIC` in `reset.ts` (and for
   the hosted databases in E00-T07), a role test "cannot create temporary tables", a line in R-31.
6. **A `tx` kept after `withTenant` returns runs in whatever transaction uses that connection next.
   (Medium)** I stored `tx`, let `withTenant(A)` finish, then used it inside `withTenant(B)`: it
   returned clinic B. With no other transaction it saw nothing. The usual cause is an un-awaited
   promise in the callback, such as `items.forEach(async …)`. Suggest: `tx` refuses work once its
   transaction has ended, and/or the type-aware lint rules `@typescript-eslint/no-floating-promises`
   and `no-misused-promises` (already installed through `eslint-config-next`; type-aware lint is
   slower). Or record it as a risk.
7. **A session-level `SET app.clinic_id` inside `withTenant` outlives the transaction. (Low)**
   `SET app.clinic_id = '<B>'` (not `set_config(…, true)`) inside `withTenant(A)`: after commit, a
   query outside `withTenant` on that pooled connection saw clinic B. Same family as R-31, but it
   reaches past the transaction. Suggest: say so in R-31; optionally `withTenant` clears the
   session value before it commits.
8. **The local-host guard in `db:reset` can be bypassed with a `host` query parameter. (Low)**
   `DATABASE_ADMIN_URL=postgres://postgres:x@127.0.0.1:5433/postgres?host=tester-guard-probe.invalid`
   passed the guard, and the script tried to connect to `tester-guard-probe.invalid` (DNS error, so
   nothing happened). pg takes `host`, `port` and `user` from the query string over the URL.
   **Should:** check the host pg will actually use, or refuse a query string that sets one. A
   non-local host, `NODE_ENV=production` and a wrong app user were refused (exit 1), as claimed.
