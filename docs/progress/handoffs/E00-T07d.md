**For the builder: what is already there** (checked on `main` at `593fc7d`)
- The case is the last one in `tests/integration/queue.test.ts`, under "the job queue as the app
  role", added by E00-T07b's critical review (`d0e81fa`). Read it whole before changing a line: it
  is about 55 lines and every assertion carries a claim.
- How it is built today: the queue is made first **as the migration role**, because `workJobs()`
  leaves an existing queue alone —
  `select pgboss.create_queue($1, '{"policy": "standard", "expireInSeconds": 1}')`. The handler waits
  for `job.signal`'s `abort`, pushes its error onto `thrown` and throws it. The `vi.waitFor`
  (30 s, every 250 ms) wants `thrown` to have length 3 **and** the job's state to be `failed`.
- Why it saw six: `retry_delay` defaults to 0 (migration 0005, `pgboss.create_queue`), so the retry
  is claimable the moment the job fails, and `pollingIntervalSeconds: 0.5` picks it up while the
  previous handler is still ending. Three attempts, two runs each.
- `pgboss.create_queue`'s policy keys are read with `options->>'…'` in
  `src/db/migrations/0005_pgboss.sql` (about line 387): `retryLimit` (default 2), **`retryDelay`**
  (default 0, whole seconds, the column `retry_delay`), `retryBackoff`, `retryDelayMax`,
  `expireInSeconds` (default 900). So a delay longer than the run is one key in the JSON this test
  already passes — no change to `src/db/queue.ts`, which sets none of them.
- The two claims to keep: `expect(job?.output).toBeOneOf([…])` and
  `expect(job?.row).not.toContain(MARKER)` (pg-boss's own words, nothing of the handler), and the
  `lines().filter(… === JOB_FAILED)` equality against `thrown.map(…)` (one `job_failed` line per
  run). The second is what the fixed count is really for: keep it true per run, not per three.
- `freshQueue()` gives each case its own queue name, `emptyJobQueue()` (`fixtures.ts`) clears every
  `pgboss` row before each case, and `migrator`/`jobsOf`/`lines()` are already in the file.
- Integration tests run one file at a time against `<db>_test`; the whole run was about 152 s before
  this task. Three attempts with a 2 s delay take about 9 s, so the 30 s `waitFor` has room.
- Must not change: `src/db/queue.ts`, `src/worker/index.ts`, any other case in the file, the
  runbook's `job_failed` row (corrected in E00-T07b's Done pass), or `tenant-allow-list.ts`.
