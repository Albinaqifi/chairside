the previous handler is still ending, "three attempts, two runs each". A probe of the same queue
(deleted, its shape is in the git history of this branch's experiments) says otherwise: with
`expireInSeconds: 1` **every job runs exactly three times**, with a retry delay of 0 s as with 3 s,
and `pgboss.job.retry_count + 1` counts those runs. The six runs came from **two jobs**: a schedule
(`* * * * *`) sends a job at every minute boundary its queue is worked over, besides the one it sends
at once. A copy of the old case started 3 s before a boundary fails every time with the red run's own
words, `expected [ … ] to have a length of 3 but got 6`; the same copy of the new case passes. So the
suggested route (a `retryDelay` longer than `expireInSeconds`) would have changed nothing, and the
overlap stays E02's real concern for a handler that ignores its signal (E02-T06, E02-T07: unchanged).
