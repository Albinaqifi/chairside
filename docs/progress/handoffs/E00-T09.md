**For the builder: what is already there** (checked on `main` at `2d6256a`)
- `src/app/(auth)/login/login-form.tsx`: `<form onSubmit={(event) => void submit(event)} …>` with
  no `method` and no `action`; the button is `disabled={pending}` only. `loginErrorMessage()` is
  exported from the same file. No test covers the form today.
- The only other form is the clinic picker, `<form action={asFormAction(chooseClinic)}>`. React
  renders it with `method="POST"`, multipart encoding and a hidden action-id field, and Next.js
  runs it without JavaScript (E00-T08's tester saw a 303 to `/login`). The logout button is a
  `type="button"` outside any form: without JavaScript it sends nothing.
- Why it also leaks with JavaScript on (React and Next.js as installed): React attaches its event
  listeners in `hydrateRoot`, which Next.js calls only after its main script has run, so a submit
  before that is the browser's own GET. `submit` is not among the events React replays once
  hydration has started. `form.submit()` fires no submit event at all.
- A POST to `/login` on Next.js 16.3.8: the proxy never runs for `/login` (its matcher in
  `src/proxy.ts`). A URL-encoded POST without the `Next-Action` header is not a server action:
  `handleAction` returns before reading the body, and the page renders
  (`next/dist/server/app-render/action-handler.js`, around lines 397 to 410). A multipart POST
  without an action id answers 500 "Failed to find Server Action" (E00-T08 tester note 5), so keep
  the default encoding.
- A form without `action` posts to the page's own URL, query string included: a page opened
  from an old `/login?email=…&password=…` in the history would send them again. Hence
  `action="/login"`.
- A disabled default button stops implicit submission by Enter: the HTML standard gives a disabled
  button no activation behaviour, and Chromium's implicit submission checks for it.
- `useSyncExternalStore(subscribe, () => true, () => false)`, with a `subscribe` defined at module
  level, gives `false` on the server and during hydration, then `true`; it passes the project's
  lint. `useEffect(() => setHydrated(true), [])` fails lint (`react-hooks/set-state-in-effect`,
  from `eslint-config-next`).
- The app renders with Next.js's own copy of React (a 19.3 canary), not the installed `react-dom`
  19.2.8. Both render the same attributes for this form (probe). The unit test uses the installed
  `react-dom/server`; the `curl` check against a production build proves what is really sent.
- The unit project collects `src/**/*.test.ts` only and runs in Node, with no DOM library.
  `useRouter()` throws outside the App Router ("invariant expected app router to be mounted"), so
  mock `next/navigation` with `vi.mock` (as the integration tests mock `next/headers`, for example
  `tests/integration/action-wrappers.test.ts`).
  `createAuthClient()` works in Node without a server. Render with `createElement` in the `.ts` file.
- The lint rule is a small type-aware rule of our own, its id added to `ARCHITECTURE_RULES` in
  `architecture.test.ts` (the shared assertion counts rule ids). Telling a function from a URL in
  `action={…}` needs type information, which the type-aware setup has for
  `src/**/*.{ts,tsx,mts}`; a `no-restricted-syntax` selector cannot. A selector block would also be
  a trap: in a flat config, a second `no-restricted-syntax` block that matches `src/modules/**`
  replaces the modules' clock and framework selectors there (as with `no-restricted-imports` in
  E00-T08). React's own type for a form's `action` is a string-or-function union, so a form helper
  typed with it is reported: E00-T04 types its actions as functions. The one form snippet already in
  `architecture.test.ts` (`<form action={save}>`) has a function action and keeps passing.
- Not built, and why (D-076): the auth library's `/sign-in/email` accepts a URL-encoded form post,
  checks its origin, and answers 200 JSON with the session token and the user. `callbackURL` only
  adds a `Location` header to that 200, which a browser does not follow. A sign-in through
  `auth.api.signInEmail` from our server code is not rate-limited: the limiter runs only in the
  library's HTTP router.

**For the tester** (the browser checks)
- Headless Chrome over the DevTools protocol, as in E00-T08, against `next start` and once under
  `pnpm dev`, with a synthetic person, an `@example.test` email and a marker password. JavaScript
  off: `Emulation.setScriptExecutionDisabled`. Scripts held back: `Fetch.enable` on
  `*/_next/static/chunks/*`, then let them continue. A script that fails: `Fetch.failRequest` on
  one chunk. `Network.requestWillBeSent` and `Page.getNavigationHistory` then show whether anything
  was sent and whether any URL holds `email=` or `password=`.
- Known and accepted (D-076): after the page has loaded, `document.forms[0].submit()` from a script
  posts to `/login` and gets the login page back: no login, and nothing leaks.
