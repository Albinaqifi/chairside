**For the builder: what is already there** (checked on `main` at `371285b`)
- `createStaffUser({ email, name, password })` (`src/modules/auth/users.ts`, from `@/modules/auth`)
  makes a user and its credential account through the auth library. It trims and lower-cases the
  email, throws a `RangeError` for a password outside the library's length limits, and throws when
  the email is taken. It goes through `getAuth()` (`better-auth.ts`: needs `BETTER_AUTH_SECRET` and
  `BETTER_AUTH_URL`) and `getDb()` (`src/db/client.ts`: the app role's pool on `DATABASE_URL`);
  `closeDb()` ends that pool, so the script can exit.
- Plain Node cannot import it: `better-auth.ts` imports `@/…`, and `./login-audit` without an
  extension (probe: `ERR_MODULE_NOT_FOUND`). tsx 4.23.15 imports `@/modules/auth` and passes Node's
  `--env-file-if-exists` on (probe). The lockfile already holds it through drizzle-kit and vite
  (`pnpm why tsx`), so `pnpm add -D tsx@4.23.15` installs nothing new.
- Grants: the app role may insert into `users` and `accounts` (`0001_auth.sql`), only read
  `memberships`, and read and update `clinics` (`0000_init.sql`). Clinics and memberships go in as
  the migration role (`MIGRATION_DATABASE_URL`), as `insertClinic()` and `insertMembership()` in
  `tests/integration/fixtures.ts` do. No table has `FORCE ROW LEVEL SECURITY`, so the migration
  role, which owns them, is not held by the policies.
- People go in through `DATABASE_URL`, the seed's own rows through `MIGRATION_DATABASE_URL`: both
  must name the same local database. `checkResetTargets()` and `connectionTarget()` in
  `src/db/reset.ts` are `db:reset`'s guard (this machine, one server, not `NODE_ENV=production`, the
  app connecting as `chairside_app`). `resetDatabase()` is what `tests/integration/global-setup.ts`
  calls; the command itself runs under `import.meta.main`. `reset.ts` stays plain Node (D-090), so
  it cannot import the seed: `db:reset` runs the two one after the other. Lint allows
  `@/modules/auth` and `pg` in `src/db/seed/` (`module-boundaries.mjs`, `database-access.mjs`).
- `clinics` (`src/modules/tenancy/schema.ts`): name, timezone, locale, currency, default_country,
  phone (E.164 check), address, email (lower-case check), status, settings (`{}`). `memberships`
  (`src/modules/auth/schema.ts`): clinic, user, role, extra_permissions, status. `ROLES` and
  `EXTRA_PERMISSIONS` come from `@/modules/auth`; each role's sidebar is in
  `src/app/(staff)/navigation.ts` and its test.
- A sign-in writes `user.logged_in` in each of the person's clinics (`login-audit.ts`), and is
  limited to 5 a minute per client address (D-063): `signInCookie(email, password, address)` in
  `fixtures.ts` takes a new address per sign-in.
- `package.json` scripts run in `cmd` on Windows: `&&` works, as `check` shows; the `db:` scripts
  load `.env` with `--env-file-if-exists=.env`. `README.md` (step 6) points to `handoffs/E00-T02.md`
  for logins made by hand.
- Do not change: what `resetDatabase()` does, `createStaffUser()`, the login rules (D-063).
- Trap: a test that seeds `chairside_test` leaves its rows for the other test files of that run.
  They make their own clinics and random emails (`testEmail()`), but check that none counts rows
  across clinics.
- The note's "Try it": `pnpm db:reset`, then a login by role. The owner has no login of their own
  yet, so this is their first.
