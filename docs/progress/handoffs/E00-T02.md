**What I built**
Login with email and password through Better Auth (D-006): sessions in our database that end
30 minutes after the last request, httpOnly cookies (Secure as soon as the app is on https),
sign-in requests limited to 10 per minute per client address with the counters in the database,
and no self sign-up. The auth tables are global (on the meta-test allow-list); `memberships` is
a tenant table with Row-Level Security. The clinic a user acts for is resolved on every request
from their active memberships, with a clinic picker for people who belong to several (D-062).
Roles and permissions are one typed table that mirrors scope-v1.md, with a pure `can()`. A
protected `(staff)` layout with a placeholder page, a plain login page, logout, and `src/proxy.ts`
for the quick redirect of requests without a session cookie.

**Findings** (what I did, what happened, what should happen)

Must fix in this task (failing tests added):

1. **`rememberMe: false` gives a 24-hour session that never ends for inactivity. (High)** Sign-in
   accepts the library option `rememberMe`. Our form does not send it, but any client can. I signed
   in with `{"rememberMe": false}`: the session row ends 86,400 s later (normal sign-in: 1,800 s),
   the cookie has no Max-Age, and the library skips the refresh for such sessions
   (`better-auth/dist/db/internal-adapter.mjs:271`, `dist/api/routes/session.mjs:170`). On the
   running app, after moving the session's created and updated times 40 minutes back, `/` still
   answered 200. **Should:** every session ends 30 minutes after its last request, whatever the
   client sends (security-privacy.md section 2: shared clinic computers). It matters more later:
   a "Remember me" box left unticked would give the longest session. Test: `auth-attacks.test.ts`,
   "ends after 30 minutes even when sign-in says rememberMe: false" (passes if the request is
   refused or the session ends within 30 minutes).
2. **A failed query during sign-in writes the typed email, or the new session's token, address and
   user agent, to the server output. (High)** On the running app I removed one grant from the app
   role for one request (INSERT on `sessions`, then SELECT on `users`; both restored and checked
   against migration 0001), then signed in. The user saw a plain 500 and our logger's JSON line was
   clean. But the library's router (better-call) also runs `console.error('# SERVER_ERROR: ',
   error)` (`better-call/dist/router.mjs:93`) with the whole Drizzle error: its message and
   `params` hold the session token, user id, client address and user agent, or the email typed
   into the form. Better Auth's `onAPIError.onError` does not prevent it: the router prints the
   line anyway. **Should:** no value a query was sent reaches any output (security-privacy.md
   section 6, criterion 7). Otherwise a database hiccup during the morning login rush puts live
   session tokens into the host's log. Tests: `auth-attacks.test.ts`, "a failed query during
   sign-in" (2 tests). They capture console, stdout and stderr, and count an error that escapes
   the handler as output, because Next.js prints what it catches.
   **The same for pages (owner, E00-T03):** I made the clinic lookup fail on `/` (EXECUTE on
   `clinics_for_user` removed for one request, then restored). The page was a plain 500, but
   Next.js printed `⨯ Error: Failed query … params: <user id>`. Today that is only an id. From E01
   the same path prints patient values from any failed page query, and the E00-T01 logger fix
   covers only errors our own code logs. Suggest: take the values out of query errors where they
   are created (the database layer), so that whatever prints them sees none, before E01. No test
   here (it needs Next.js rendering); board, Discovered.
3. **`/verify-password` lets a signed-in session try 100 passwords per 10 seconds. (Medium)** It
   is one of the library's routes under `/api/auth/*`, tagged `scope: "server"` in the library
   but served over HTTP. No special rule covers it, so the library default applies: 100 requests
   per 10 s per address, 600 a minute, against our 10 a minute at sign-in. I made 120 wrong
   guesses from one address: 100 were answered, then 429. Anyone at a clinic computer left signed
   in (the case the 30 minutes exist for) can guess that person's password 60 times faster than
   at the login form. `/change-password` also checks the current password, at the library's
   3 per 10 s (18 a minute). **Should:** no route checks a password faster than sign-in allows.
   Nothing uses `/verify-password` before E04. Test: `auth-attacks.test.ts`, "is limited like
   sign-in: /verify-password" (passes with a 429 after 10 tries or with the route switched off).
4. **`can()` answers `undefined` for a role it does not know, and counts a missing `providerKind`
   as linked. (Low)** `can('admin', …)` returns `undefined` (the `switch` has no default).
   Extras without `providerKind` give an owner `visit.record` (`undefined !== null`). Typed code
   cannot do this; a database row or a JavaScript caller can, and `if (can(…) === false)` would
   then let it through. **Should:** `false`. Test: `permissions.test.ts`, "answers false, never
   undefined, for a role or link it does not know".

For the owner to decide (no failing tests):

5. **Any client picks its own rate-limit counter by sending `X-Forwarded-For`. (Medium now; High
   if staging is reached the same way)** On `next start` without a proxy: 12 wrong passwords,
   each with a different `X-Forwarded-For`, gave 12 × 401 and never a 429. Next.js passes the
   client's header on unchanged, and the library trusts any single value
   (`@better-auth/core/dist/utils/ip.mjs:190`). Without the header the socket address is used
   (limited after 10). With two values all requests share the `no-trusted-ip` counter. So
   criterion 6 holds only behind a proxy that overwrites or appends the header. R-33 describes
   only the lockout side. Suggest: E00-T07 sets the trusted proxies or the host's own header, and
   its acceptance gets "rotating `X-Forwarded-For` against staging still gets a 429". The owner
   may want to look at D-064 point 5 again: a per-account limit stops targeted guessing however
   the address is faked. (The builder's own test depends on this behaviour: it uses a new address
   per test.)
6. **An action will run in whatever clinic the cookie names when it arrives, not the clinic the page
   was shown for. (Medium, design, for E00-T03)** There is one clinic cookie per browser. If tab 1
   shows clinic A and tab 2 switches to B, tab 1's next request acts in B. When the picked clinic's
   membership is disabled, the next request moves to the person's other clinic without a word
   (seen above, as D-062 designs it). Reads are fine, because the header names the clinic. Writes
   are not: a form shown for A and sent after a switch would be carried out in B. Suggest: E00-T03's
   wrapper receives the clinic id the page was rendered with and refuses when it differs from the
   resolved clinic, or the clinic goes into the URL.
7. **A signed-in person can rename themselves and store any picture address. (Low, for E04)**
   `/update-user` with a new name → 200, the name changed. With an `image` URL on another server →
   stored. Changing the email is refused, and `/change-email` and `/delete-user` are switched off.
   Names appear in the header and will appear in audit views. A stored outside image shown later
   would let that server see every viewer. Decide in E04, or switch the route off until then.
