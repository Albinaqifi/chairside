**The flaky case: cause.** Found in the log line of a reproduced failure (5 in 120 pairs), a code and no value: `23505`, constraint `patients_clinic_id_id_key`. `patients.id` is unique twice, by the primary key and with the clinic (the composite foreign keys need that); `ON CONFLICT (id) DO NOTHING` covers only the first. Two inserts of one id at the same moment can both pass the first check and meet in the second index, where a unique violation is an error, so one send answered `internal` instead of `already_booked`. Not a wait past 5 s, so no barrier is needed. The fix is a real one: `ON CONFLICT DO NOTHING` without a target (the table has those two unique indexes only). Proof: the 200-pair test in `patients-update-locks.test.ts` fails with the old target (35 rejected sends) and passes now; the case itself ran 20 times in a row green, and 300 repeats of it once, green. No expectation was changed.
