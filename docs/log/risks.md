Add a risk when you see one; update "Status" when something changes. Never delete a row.

| R-31 | **Tenant context switched inside a transaction, or rows carried past it.** The clinic that Row-Level Security uses is a transaction setting (`app.clinic_id`). Any SQL run inside `withTenant` could change it with `set_config` or `SET` and reach another clinic's rows; PostgreSQL cannot prevent that. Session state that outlives the transaction, such as a session-level `SET app.clinic_id` or a cursor declared `WITH HOLD` (E00-T01 testing, findings 7 and 15), no longer reaches the next user of a pooled connection: `withTenant` resets every connection with `DISCARD ALL` (D-061). **Large objects** are not covered: they are stored database-wide, outside Row-Level Security, and creating one needs no privilege. SQL inside one clinic's `withTenant` can copy rows into a large object (`lo_from_bytea`, `lo_put`), and SQL in another clinic's transaction can read it by its number (`lo_get`). Blocking them needs superuser rights (revoking the large-object functions from PUBLIC), which a hosted database may not give. | L | H | Only `src/db/tenant.ts` sets the clinic (`CLAUDE.md` conventions); reviewers look for `app.clinic_id`, `set_config`, `SET` and large-object functions (`lo_…`) in every diff; cross-clinic work only through named database functions (`security-privacy.md`, section 1). A lint rule could ban the setting's name outside `src/db`. Large objects (not done): a meta-test check that the database holds none (`pg_largeobject_metadata`), and revoking the functions wherever we have superuser rights (local now, hosted in E00-T07). Found in E00-T01. | Albin | Open |
| R-32 | **A `tx` used after its `withTenant` has returned.** A promise in the callback that is not awaited (for example `items.forEach(async …)`) can run its query after the transaction has ended. It then runs in whatever transaction uses that pooled connection next, possibly another clinic's, or with no clinic at all. | M | H | To solve in E00-T03: type-aware lint rules for un-awaited promises (`@typescript-eslint/no-floating-promises` and `no-misused-promises`, already installed through `eslint-config-next`), and/or a `tx` that refuses work once its transaction has ended. Until then, reviewers check that every promise inside `withTenant` is awaited. Found in E00-T01 testing (finding 6). Moved to E00-T08 when E00-T03 was split; the lint rules are the chosen option (D-071). Since E00-T08, `pnpm lint` fails on a promise in `src/` that is not awaited: `no-floating-promises` with `checkThenables`, because a Drizzle query is a thenable, not a Promise, and `no-misused-promises` for `items.forEach(async …)` (D-074). Still passing: a promise marked `void` on purpose (reviewers check any `void` inside `withTenant`), and `.js`/`.cts` files in `src/`, which tsconfig.json does not include (none exist). Since E00-T10, a statement that only hangs `.catch(…)` or `.then(ok, fail)` on a promise fails lint in the `.ts` and `.mts` files of `src/` and in every module file (`no-floating-promises` counts it as handled), a rejection with anything but an Error fails it too (`prefer-promise-reject-errors`), a `.js`, `.jsx`, `.mjs`, `.cjs` or `.cts` file in `src/` fails a test, and no lint comment in `src/` switches these rules off (D-077). Still passing: `void`, as before, and such a statement in a `.tsx` file. | Albin | Mitigated by lint (E00-T08, E00-T10) |
| R-33 | **Login rate limit by client address.** A clinic's computers usually share one public address: ten sign-in requests from it within a minute (successful ones count too) block login for everyone at that address for up to a minute, and someone on the same network can do it on purpose. Without a trustworthy address, all such requests share one bucket. | M | L | The limit is 10 per minute (raised from 5 in D-064), so a lock is short; counters are per address and path, in the database.
